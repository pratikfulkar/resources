P-01 / SPEC Start here

Behavioral Verification Engine

An independent checker that catches when an AI code-migration agent silently changes business logic — instead of trusting the same model to grade its own work.
DifficultyMedium–High
Domain fitDirect — your own stack
V1 build time~3–4 weeks
Problem

Legacy modernization tools translate syntax but routinely drop implicit business rules — edge cases, validation branches, exception handling — because there's no independent way to verify old and new code behave the same. Research shows models can't reliably self-judge their own migration output.

Use-case basis
  • An engineer runs an AI migration agent on an Express route and wants proof it didn't change behavior before merging.
  • A team wants a CI gate that blocks merges when AI-modernized code diverges from the original on generated edge-case inputs.
  • A hiring panel wants to see you reason about trusting — or not trusting — AI-generated code changes in production systems.
V1 checkpoints
  1. Pick one real pattern
    Choose a single legacy pattern you've actually built — e.g. conditional form-validation logic.
    pattern is written down as legacy input + expected modern output
  2. Build input generation
    Use property-based testing to generate a wide range of inputs for that function, not just happy-path examples.
    100+ generated inputs cover every branch in the function
  3. Build the dual-run harness
    Run legacy and modernized code against the same generated inputs in isolated containers; capture outputs and errors.
    both versions run headless and log structured output for every input
  4. Build the diff engine
    Compare outputs: exact match, equivalent-but-different-shape, or clear drift. No AI needed yet.
    a deliberately-broken migration gets flagged; a correct one passes clean
  5. Wire in an AI migration agent
    Only now add the AI layer: an agent that performs the migration, verified by the harness you already trust.
    one full run: legacy in → agent migrates → harness scores it
Stack
Language TypeScript / Node.js
AST parsing ts-morph
Test generation fast-check (property-based)
Sandboxing Docker
LLM SDKs Anthropic + OpenAI
CI packaging GitHub Actions
Why this one: existing academic work (AgentModernize) still has an unsolved code-generation reliability gap, and a 2026 AWS-affiliated study found models can't reliably self-review their own modernization. You're not competing to build a better migration agent — you're building the trust layer in front of any of them, using a benchmark drawn from your own production domain.

P-02 / SPEC Alternate

Agent Trajectory Evaluation Platform

Scores how an agent reached an answer — which tools it called, whether it looped, whether it recovered from a bad step — not just whether the final answer was right.
DifficultyMedium–High
Domain fitGeneral — no personal edge
V1 build time~2–3 weeks
Problem

Most agent evaluation checks only the final answer. That misses looping, wrong-tool calls that got silently retried, and unsafe intermediate steps — the actual reasons production agents fail even when benchmark scores look fine.

Use-case basis
  • A team ships an agent that passes offline evals but fails in production, and needs to see the step-by-step trace to know why.
  • An engineer wants to compare two agent designs on efficiency (steps taken, retries) not just correctness.
  • A hiring panel wants to see you reason about agent reliability at the trajectory level, which most eval tutorials skip.
V1 checkpoints
  1. Build one simple tool-using agent
    3 tools max — e.g. a support agent with lookup, search, and reply tools.
    agent completes a basic task end to end
  2. Instrument every step
    Log each tool call, its arguments, its result, and the agent's stated reasoning as structured trace data.
    a full run produces a readable, ordered trace, not just a final answer
  3. Define trajectory scoring rules
    Right tool for the task? Right argument? Did it loop or retry without progress?
    a deliberately-looping run scores worse than a clean run on the same task
  4. Build a minimal dashboard
    Visualize one run's trajectory as a timeline, with flags on the steps that scored poorly.
    you can point at a specific step and say why it was flagged
Stack
Language TypeScript / Node.js
Tracing OpenTelemetry-style spans
Agent orchestration Hand-rolled state machine
Dashboard Next.js
LLM SDKs Anthropic + OpenAI
Why keep this as an alternate: the gap is real and well-documented — enterprise agent pilots rarely reach production, and compounding step failures are the reason. But this is more generic infrastructure; without a personal domain angle it competes directly with existing eval tooling on polish rather than on a story only you can tell.

P-03 / SPEC Backup

MCP Tool-Poisoning Semantic Scanner

Detects malicious or deceptive instructions hidden in MCP tool descriptions — existing open-source scanners rely on pattern matching and carry a high false-positive rate.
DifficultyMedium
Domain fitSecurity niche
V1 build time~2–3 weeks
Problem

A confirmed malicious MCP server was distributed via npm in 2025 and silently exfiltrated data before detection. Current open-source scanners catch this with YARA-style pattern matching, which one 2026 audit found produces a false-positive rate near 78% — too noisy to trust.

Use-case basis
  • A developer installing a new MCP server wants to know if its tool descriptions contain hidden instructions before connecting an agent to it.
  • A security-conscious team wants fewer false alarms than existing pattern-matching scanners produce.
  • A hiring panel in a security-adjacent AI role wants to see precision/recall reasoning, not just "I built a scanner."
V1 checkpoints
  1. Build a labeled test set
    15–20 MCP tool descriptions: some clean, some with injected hidden instructions you write yourself.
    the set is labeled and versioned before any detector is built
  2. Build a baseline pattern matcher
    A simple keyword/regex scanner, mirroring what existing tools do — this becomes your comparison baseline.
    baseline produces a precision/recall number on your test set
  3. Build a semantic classifier
    An LLM-based classifier that reasons about intent in the tool description, not just keywords.
    semantic classifier beats the baseline's precision on the same test set
  4. Package as a CLI scan tool
    Point it at a live MCP server config and get a report.
    running it against a real public MCP server produces a readable report
Stack
Language TypeScript / Node.js
MCP integration MCP SDK (client)
Classifier Anthropic / OpenAI SDK
Baseline matcher Regex / YARA-style rules
Packaging Node CLI
Why keep this as backup: it's a real, current, unsolved precision problem, not a saturated market — but it's narrower and more security-specialist than the other two, which may point you toward security-adjacent roles specifically rather than general AI/backend roles.
